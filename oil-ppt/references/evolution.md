## 目标

oil-ppt 不是模板集合，而是一套面向模型的演示设计接口。模型提交结构化的内容意图，程序把容易重复出错的设计动作变成稳定能力。

始终保持三个结果：

- 内容关系清楚，观众能迅速判断先看哪里、记住什么。
- 不同项目可以改变配色、素材、密度和气质，但不牺牲可读性。
- 能力较弱的模型不需要寻找隐藏文件、记忆 CSS 或同时做大量视觉选择。

## 职责边界

模型负责需要语义判断的事情：

- 理解受众、场景、核心观点和叙事顺序。
- 判断内容是焦点、顺序、并列、对比、汇聚、证据还是图文关系。
- 说明素材展示什么、回答什么问题，以及哪条信息最重要。
- 使用用户提供或可核验的事实，不编造案例、数据和引用。

程序负责可重复、可测量、容易出错的事情：

- 16:9 页面画布、等比缩放、安全区、网格、间距和内容边界。
- 组件比例、字号下限、图标容器、图表几何、背景和局部装饰。
- 素材槽位、裁切、外框归属、文件检查和项目内路径。
- 状态推进、合法组合、文字溢出、视觉节奏和构建验证。

用户负责确认大纲、事实、素材和正式预览。程序不能替用户确认，模型不能伪造确认状态。

## 为什么优先程序化

弱模型的主要风险不是不会写 HTML，而是一次需要记住太多互相影响的选择。每减少一个无必要的选择，最终设计就更稳定。

满足以下任一条件时，优先把能力放进程序：

- 每次制作都会重复发生。
- 能通过结构、尺寸、数量、路径或浏览器结果验证。
- 出错后会影响多页或最终构建。
- 不同模型容易产生不一致实现。
- 已有明确的设计系统答案，不需要每次重新发明。

保留给模型的自由度应集中在内容判断和叙事取舍，不应浪费在圆角、阴影、间距、图标尺寸或裁切算法上。

程序化能力必须通过 CLI contract、schema 或检查结果暴露。不能只写在某个模板、参考文件或注释里，等待模型偶然发现。

## 面向弱模型的接口

- 始终提供一个统一 CLI 入口和唯一下一步命令。
- 先返回紧凑组件目录，再按组件查询详细 contract；不要要求遍历模板文件。
- 使用封闭枚举、固定字段和明确数量，避免用自然语言描述隐含结构。
- 复杂 variant 的 contract 先给 `minimum`，再给 `optional`；模型优先提交最小合法输入。
- 可选字段缺省时必须自然收拢，不留下空胶囊、空图注或仅用于装饰的占位区域。
- 推荐器只在内容特征足够明确时给出高置信建议，不替模型猜测主题。
- 错误信息同时说明位置、原因、需要修改的字段和下一条命令。
- 让结构化输入成为唯一事实来源，不要求模型同步修改多份重复配置。
- 公开示例必须使用推荐默认值并展示核心能力；不能为了最短而示范会关闭能力的逃生选项。
- 关闭质量门禁的选项不得出现在默认示例中，并且必须要求用户显式确认。

模型调用一个命令后，程序应完成所有可确定的内部步骤。不要把内部脚手架、复制、同步或验证拆成模型必须记住的长流程。

## 不设计 fallback 链

每个合法输入只对应一条可预测的执行路径。

- 缺少必要字段或素材时明确失败，不生成默认文案、默认占位图或空卡片。
- 不支持的模板、variant、背景或装饰直接报错，不静默切换成其他选项。
- 素材处理失败时保留原文件并停止，不尝试一串不可见的替代方案。
- 不捕获并忽略会影响结果的异常。
- 新能力不得增加只为兼容旧名字的运行时 alias。
- 旧格式需要保留时，提供显式迁移或入口标准化，并尽快删除旧路径。

当程序无法继续时，返回一个清楚的阻塞原因。简单失败比表面成功但结果不可预测更可靠。

## 组件设计

只有出现新的信息关系、阅读路径或主要页面轮廓时才新增组件。颜色变化、左右镜像、装饰变化和局部间距调整不构成新组件。

每个组件必须定义：

- `use_when` 与 `avoid_when`。
- family、silhouette、主要阅读路径和视觉重心。
- 必填字段、字段数量、内容预算和可选字段。
- 主叙事、支撑内容和元信息的面积关系。
- 素材角色、推荐比例、是否允许裁切以及外框归属。
- 合法 variant、decor 和背景范围。
- 在整套演示中承担的节奏作用。

组件必须保持业务无关。模板、测试数据和参考文档不得写入某个具体项目的产品、人物或业务文案。

复合组件可以包含多个区域，但只能有一个主要视觉中心和一条清楚的阅读顺序。内容不足时应换用更聚焦的组件，不用空模块补齐结构。

复刻参考页面时优先冻结核心构图：区域比例、阅读顺序、视觉中心、色彩层级和关键容器必须稳定；图注、来源小字、角标与辅助徽章属于可选增强，不把逐个微小元素一致设为合法输入的前提。

## 视觉原则

- 用面积、位置、底色和留白建立层级，不使用组件阴影和嵌套外框。
- 装饰保持浅、少、局部，只使用系统公开的点阵、圆环、三角形、斜切或块面语言。
- 图标统一进入容器，使用同一图标家族；图标只在能缩短理解时间时出现。
- 图表必须由真实数值生成，不能用装饰性柱形或折线冒充数据。
- 真实截图和材料优先保真，不让图片模型重画其中的文字、界面和数据。
- 标题高亮只用于真正需要记住的短语，颜色和透明度由 runtime 管理。
- 页面内容少时放大核心关系，内容多时重组、拆页或使用密度组件，不依赖无限缩字。

具体阈值和当前视觉 token 以程序 contract、runtime 与检查结果为准，不在本文件重复维护。

## 屏幕比例适配

演示内容始终保持 16:9 页面画布，不针对显示设备比例重新排版。

- runtime 按 `min(容器宽度 / 1920, 容器高度 / 1080)` 等比缩放并居中。
- 非 16:9 屏幕使用中性留白承接多余区域，不拉伸、不裁切、不产生演示滚动。
- 嵌入网页时根据实际外层容器计算，不只读取浏览器宽度。
- 手机和竖屏仍完整显示 16:9 页面；控制界面可以响应式变化，演示内容不能重排。
- `cover` 式裁切只属于明确允许裁切的媒体槽位，不能用于整页适配。

显示比例是 runtime 的责任，模型和模板不增加设备专用分支。

## 变更流程

1. 先说明缺少的是哪种内容关系、程序能力或质量门禁。
2. 判断它应由模型、程序还是用户负责；能稳定验证的优先交给程序。
3. 先更新唯一数据契约，再实现模板、填充器、推荐器、素材计划和验证。
4. 使用通用内容建立最小回归演示，不使用正在处理的业务项目作为模板示例。
5. 把新能力加入 CLI contract 和完整能力展，确保弱模型能够发现。
6. 检查 16:9 原始页面、缩放预览、非 16:9 容器和移动端控制界面。
7. 运行 schema、媒体、溢出、浏览器、组合矩阵和端到端构建验证。
8. 删除被替代的分支、旧字段和重复说明，不把历史实现继续叠加。
9. 只有用户工作流程发生变化时才修改 `SKILL.md`；程序内部变化不要写入日常指令。

## 合并门槛

一次变更只有同时满足以下条件才算完成：

- 弱模型可以通过统一入口发现并调用。
- 不需要模型手写布局 CSS 或复制内部脚本命令。
- 非法输入明确失败，没有占位内容和静默降级。
- 组件在通用内容下成立，没有具体业务依赖。
- 页面无文字、素材和装饰溢出。
- 能力展展示真实 runtime 结果，不使用另做的示意图。
- 完整组件组合、桌面、移动端和最终构建验证通过。
- `SKILL.md` 没有重复程序已经执行的细节。
